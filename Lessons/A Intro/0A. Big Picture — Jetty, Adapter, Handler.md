# 0A. Big Picture — Jetty, Adapter, Handler

## Purpose

This lesson answers one question:

> When a browser or `curl` sends a request, what happens before your Clojure function runs?

Do not touch code yet. First build the picture.

---

## 1. Explain it to a 10-year-old

Imagine a small restaurant.

| Restaurant story | Web server idea |
|---|---|
| Customer | Browser, `curl`, or HTTPie |
| Customer's order | HTTP request |
| Front desk worker | Jetty |
| Translator | Ring Jetty adapter |
| Cook | Your Ring handler |
| Clean order ticket | Ring request map |
| Finished tray | Ring response map |

Simple story:

> The customer gives an order to the front desk. The front desk understands the outside-world mess. The translator rewrites the order into a clean ticket. The cook reads the ticket and makes the food. Then the translator and front desk send the finished tray back to the customer.

Technical story:

> Jetty receives and parses HTTP. The Ring Jetty adapter turns Jetty's Java request object into a Clojure request map. The Ring handler receives that map and returns a response map.

---

## 2. The three jobs

### Jetty

Jetty is the Java web server.

Jetty does outside-world work:

- listens on a port
- accepts network connections
- reads bytes from the socket
- parses HTTP
- handles connection details
- writes the final response bytes back to the client

Feynman version:

> Jetty is the front desk. It talks to the outside world.

Do not say:

> My Clojure handler reads from the socket.

Better:

> Jetty reads from the socket. My handler receives a Clojure map.

---

### Ring Jetty adapter

The Ring Jetty adapter is the bridge.

It translates:

```text
Jetty Java request object  →  Ring Clojure request map
Ring Clojure response map  →  Jetty Java response object
```

Feynman version:

> The adapter is the translator. It rewrites Jetty's request into a form Clojure code likes.

---

### Ring handler

A Ring handler is just a Clojure function.

It receives one value:

```clojure
request
```

It returns one value:

```clojure
response
```

Basic shape:

```clojure
(defn handler [request]
  {:status 200
   :headers {"Content-Type" "text/plain"}
   :body "Hello from Ring"})
```

Feynman version:

> The handler is the cook. It reads the clean order ticket and returns a finished tray.

---

## 3. The full path of one request

When you run:

```bash
curl 'http://localhost:3000/todos?id=3'
```

The simplified path is:

```text
curl
  ↓
network connection
  ↓
Jetty receives bytes
  ↓
Jetty parses HTTP
  ↓
Jetty creates Java servlet request object
  ↓
Ring Jetty adapter creates Ring request map
  ↓
handler receives request map
  ↓
handler returns response map
  ↓
Ring Jetty adapter creates Java servlet response object
  ↓
Jetty writes HTTP response bytes
  ↓
curl prints the result
```

The important boundary:

```text
Java servlet world  →  Ring Clojure data world
```

That boundary is the adapter's job.

## 6. Wrong ideas to kill early

### Wrong idea 1

> Jetty calls my route directly.

Better:

> Jetty receives and parses the HTTP request. The Ring adapter calls the Ring handler.

### Wrong idea 2

> My handler parses HTTP.

Better:

> Jetty parses HTTP. My handler receives a Ring request map.

### Wrong idea 3

> The request map is raw HTTP.

Better:

> The request map is Clojure data made from a parsed HTTP request.

### Wrong idea 4

> The handler is the web server.

Better:

> Jetty is the web server. The handler is the Clojure function that decides the response.
